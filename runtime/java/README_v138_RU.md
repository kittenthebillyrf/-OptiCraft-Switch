# v138 — проверка точки входа оригинального Minecraft

Этот этап проверяет не суррогатную игру, а реальный класс
`net.minecraft.client.Minecraft` из пользовательского `minecraft.jar`.

## Запуск аудита на Windows

```powershell
py tools/audit_java125_entrypoint.py "E:\switch\opticraft\minecraft.jar"
```

Скрипт извлекает метод `main(String[])`, его байткод и ссылки Constant Pool на Java/LWJGL API. Сам JAR не меняется и не копируется в репозиторий.

## Почему NRO пока не может запустить игру

Проверка исходного JAR показывает, что `Minecraft.main(String[])` не является простым вызовом одной функции. Он использует массив строк, `StringBuilder`, системное время, long-арифметику и вызывает статический метод класса Minecraft. Дальнейший запуск требует полноценной цепочки загрузки классов, инициализации классов, объектов/массивов, Java SE API и LWJGL.

Текущий C++ bytecode interpreter поддерживает лишь ограниченное подмножество инструкций и не является полной JVM. JNI input bridge — только мост ввода, а не реализация JNI_CreateJavaVM. Поэтому честный результат на этом этапе: точка входа найдена и исследована; вызов оригинального `main()` на Switch пока не работает.

Следующий блокирующий этап — объединить classfile parser, class loader, heap/object runtime и interpreter в один runtime, затем реализовать недостающие инструкции и Java SE классы, нужные по фактическому графу зависимостей Minecraft. Нельзя объявлять запуск успешным, пока оригинальный JAR реально не доходит до игрового окна на Switch.
